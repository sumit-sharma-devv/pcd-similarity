PCD Similarity – Documentation

What the project does, which metrics it uses, what they mean, and how the similarity score is computed.

1. Overview

PCD Similarity compares two 3D point clouds stored as .pcd files (the Point Cloud Library format) and reports how similar they are. You upload file A (the reference) and file B; the tool returns a single headline similarity percentage, several supporting distance metrics, and an interactive 3D view with both clouds overlaid.

The headline score is based on the Density-aware Chamfer Distance (DCD) proposed in Wu et al., NeurIPS 2021 (arXiv:2111.12702), a metric designed to compare point sets more faithfully than the classic Chamfer Distance.

Everything runs in your browser. The files are read locally and are never uploaded to a server.

What has been built

  • A PCD reader supporting ascii, binary and binary_compressed (LZF) data, which extracts the x y z coordinates.
  • Five metrics: Density-aware Chamfer Distance (primary), Chamfer Distance (L1 and L2), Hausdorff Distance, and F-score.
  • A kd-tree nearest-neighbour search so that clouds of up to 200,000 points compare in about a second.
  • An interactive 3D viewer (rotate, pan, zoom, preset views, auto-rotate, fullscreen, mouse, touch and keyboard controls).
  • Two interchangeable implementations that give the same numbers: this static JavaScript site, and a Python/Flask app.

2. How it works

  1. Parse. Each file's header is read (FIELDS, SIZE, TYPE, POINTS, DATA) and the x, y, z values are extracted. Points with non-finite coordinates (NaN padding) are dropped. Other fields such as colour or intensity are ignored.
  2. Subsample. A cloud with more than 200,000 points is randomly reduced to 200,000 (fixed seed, so repeated runs agree).
  3. Normalise (optional, on by default). Both clouds are translated so the centroid of A is the origin, then divided by the largest distance from that centroid to any point of A. A therefore fits inside a unit sphere and its frame is shared with B. Because the same transform is applied to both, a real difference in size or position between A and B is still penalised.
  4. Nearest neighbours. For every point of A the closest point of B is found, and vice versa, using a kd-tree. This yields two lists of distances and, for each matched point, how many points chose it.
  5. Metrics. All five metrics are computed from those distances and counts.
  6. Display. Up to 20,000 points per cloud are shown in the viewer, in the same normalised frame as the metrics.

3. The primary metric: Density-aware Chamfer Distance

Background: Chamfer Distance and its weakness

The Chamfer Distance (CD) measures how far each point of one cloud is from its nearest neighbour in the other, in both directions. It is cheap and widely used, but it only looks at nearest-neighbour distance. Two clouds can therefore score a perfect CD while having very different point densities: if a thousand points of A all sit on one point of B, CD does not notice, because every distance is still tiny. Its values are also unbounded, so a few outliers can dominate.

Definition

Let S₁ and S₂ be the two point sets. For a point x in one set, let ŷ be its nearest neighbour in the other set. Then:

DCD(S₁, S₂) = ½ · ( 1/|S₁| · Σₓ∈S₁ [ 1 − (1 / n_ŷ) · exp(−α · ‖x − ŷ‖₂) ] + 1/|S₂| · Σ_y∈S₂ [ 1 − (1 / n_x̂) · exp(−α · ‖y − x̂‖₂) ] )
  • ‖x − ŷ‖₂ is the Euclidean distance to the nearest neighbour.
  • exp(−α·d) turns that distance into a closeness value between 0 and 1: it is 1 when the points coincide and decays towards 0 as they separate. α sets how quickly (default 1000, the paper's value).
  • n_ŷ is the density term: the number of points of the querying set whose nearest neighbour is that same ŷ. If many points pile onto one target, each one's contribution is divided by that count, so the clump is penalised. For a one-to-one matching n = 1 and the term has no effect.

Why it is useful

  • Density-aware: mismatched local density lowers the score even when the shapes line up, which plain CD cannot detect.
  • Bounded: every term lies between 0 and 1, so DCD is always in [0, 1] and is not dominated by outliers.
  • Cheap: it needs only nearest-neighbour queries, unlike the Earth Mover's Distance, which requires an optimal matching.

4. How the similarity score is measured

The headline number is simply:

similarity = 1 − DCD(A, B) (shown as a percentage)

So 100% means the clouds coincide point for point, and 0% means no point has a close neighbour. Lower DCD and higher similarity are both better.

The score is deliberately strict. With the default α = 1000, a nearest neighbour at distance 0.001 (in normalised units) contributes e⁻¹ ≈ 0.37, and at 0.01 it contributes only ≈ 0.00005. Two scans of the same object that sample different points, or that differ by sensor noise larger than about 0.1% of the object's size, will score close to 0%. The paper uses this setting to compare reconstructions of dense clouds against ground truth. For noisier real-world data, lower α (for example 10–100) in the options to get a more graded score. Compare scores only between runs that use the same α.

5. Supporting metrics

Shown alongside the headline score for context. In all of them d(x→B) is the distance from a point x of A to its nearest point in B, and d(y→A) likewise for a point of B.

MetricDefinition used hereMeaningBetter
Chamfer Distance (L1) ½ · ( mean d(x→B) + mean d(y→A) ) Average distance from a point to the other cloud's surface, both ways. Easy to read in the same units as the normalised coordinates.Lower
Chamfer Distance (L2) ½ · ( mean d² + mean d² ) Same, with squared distances, so large gaps are punished more.Lower
Hausdorff Distance max( max d(x→B), max d(y→A) ) The single worst-case gap: how far the most isolated point is from the other cloud. Very sensitive to outliers.Lower
F-score 2·P·R / (P + R) where P = share of B's points within τ of A, and R = share of A's points within τ of B How much of each cloud is covered by the other at a tolerance τ (default 0.01 in normalised units). Between 0 and 1.Higher

The Chamfer values here average the two directions. Some papers sum them instead, so they differ from such figures by a factor of two.

6. Worked example

Two synthetic checks, computed with α = 100 and τ = 0.05 (a softer setting than the default):

Sphere of 6,000 points vs. its first 5,000 points with a little noise (σ = 0.002) and 300 extra copies of one point62.83%0.00490.07200.996
Sphere of 6,000 points vs. a different random sphere, 5% larger and shifted slightly0.84%0.05730.10790.370

The first pair is geometrically almost identical (F-score near 1, tiny Chamfer), yet its similarity is only about 63%. That loss comes from the density term: the 300 duplicated points all share one nearest neighbour, which DCD penalises and plain Chamfer Distance would ignore. The second pair is a genuine mismatch in size and position, and the score collapses.

7. Reading the results

You seeIt suggests
High similarity, low Chamfer, high F-scoreThe clouds match closely in both shape and density.
Low similarity but low Chamfer and high F-scoreThe shapes agree but density or point multiplicity differs, or α is too strict for the amount of noise.
Low Chamfer but large HausdorffMostly aligned, with a few outlier points or a missing region.
High Chamfer and low F-scoreThe clouds differ in shape, scale or position (or are not aligned).

8. Limitations and notes

  • No alignment. The tool does not register the clouds. If B is rotated or shifted relative to A, the score drops. Align them first (for example with ICP) if pose should not matter.
  • A is the reference. Normalisation uses cloud A's centroid and extent, so swapping A and B can change the numbers slightly. Turning normalisation off compares the raw coordinates, in which case α and τ are in the files' own units.
  • Geometry only. Colour, intensity and normals are ignored.
  • Subsampling. Clouds above 200,000 points are randomly subsampled, so results for such files are estimates and the viewer shows at most 20,000 points.
  • Scale of α. The score depends strongly on α and on the units; it is a relative measure for comparing runs with the same settings, not an absolute percentage of "sameness".
  • Testing. The code was checked on synthetic clouds, including agreement between the JavaScript and Python implementations. It has not been benchmarked on real scanner data, and the compressed (LZF) format was verified only on a small hand-made case.
  • The DCD was implemented from the definition in the paper rather than from the authors' code, so tiny numerical differences from other implementations are possible.
